# Updating

## Choose a channel

From the version menu at the top right, open **Opciones → Actualizaciones → Canal** and save:

| Channel | Builds offered |
| --- | --- |
| **Estable** (default) | Published stable releases with a valid update package. |
| **Alpha** | Successful builds from the active release PR, with stable releases as a fallback. |

The selection is stored on the server and applies to the installation. Switching channels does not install anything. Older versions are never installed automatically; an Alpha installation can return to Estable when a newer stable version is available.

If you installed `0.3.1-alpha.24`, builds `0.3.1-alpha.1` through `0.3.1-alpha.23` are considered older and will not be offered as updates. The next higher Alpha or the stable `0.3.1` can be installed when published.

The application checks in the background while open. Version checks are cached for five minutes on Alpha and six hours on Estable. **Buscar actualizaciones** refreshes the cache, subject to a one-minute throttle and GitHub rate-limit backoff.

GitHub permits 60 unauthenticated API requests per hour per server IP, shared with other applications using that IP. This limit applies when resolving or downloading a new release; routine version checks use the application version service without querying the GitHub API. When limited, Actualizaciones shows the UTC retry time and pauses checks until then; refreshing cannot bypass that pause. An HTTP 403 without rate-limit evidence is reported as denied access instead.

## Server requirements

- PHP ZIP and cURL extensions, HTTPS access to the version service and GitHub, with working CA certificates.
- Write access to application files, private `config/` state and `backups/`.
- For a private repository, a fine-grained token with **Contents: read** and **Pull requests: read** for the repository. Set `github_token` in `config/local.php` or `F125_GITHUB_TOKEN` in the web PHP environment. A public repository needs no token.

There is no separate updater password or ZIP upload form. Downloads are restricted to the project repository.

## Install an update

1. Save or export your draft and finish work in other tabs.
2. Open the version menu and select **Actualizaciones** and review the available version, commit and release notes.
3. Click **Actualizar**.
4. Check the installed version after the page reloads.

Before installation, the application rechecks the selected release, verifies the GitHub SHA-256 digest and matches its version, channel, PR and commit against the package manifest. PHP requirements and database schema compatibility are checked before replacing files.

Configuration, channel settings, installation state and MariaDB data are preserved. Packages requiring a different base schema are rejected. Compatible catalog additions are applied separately after the file update: back up MariaDB, then open **Opciones → Actualizar base de datos**. See [database migrations](database-migrations.md).

## Initial upgrade from 0.2.x

The old updater cannot fetch GitHub builds. Incorporate the new `src/`, `data/` and public-directory files once using your hosting tools. Preserve `config/local.php` and `config/installation.json`. Later updates use the web interface. The old `update_key` setting is no longer used.

The package uses `public_html/` as its logical public path. The installer maps it to the actual public directory, including `www/` or `public/`.

## Limits and recovery

Downloads are limited to 8 MB; extracted content to 16 MB, with at most 2 MB per file.

Before replacing files, the updater saves their previous contents in `backups/update-DATE-ID/` and writes a private journal. Concurrent application requests receive a temporary 503 response during replacement. If the process is interrupted, the next request attempts recovery before loading the application.

Keep the backup if automatic recovery fails. Restore its files to their original locations; map the backup's `public_html/` contents to your actual public directory. Remove `config/update-journal.json` only after completing and checking the manual restoration. MariaDB backups remain separate.

## Build and publish

See [the release workflow](releasing.md). Packages are generated by `bin/package.py` and are attached to GitHub releases; GitHub's generic source ZIP is not an update package.
